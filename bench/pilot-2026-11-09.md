# L3 pilot — 2026-11-09 (2 tasks, n = 2 per arm)

This is the first run of the A/B kit. It proves the *mechanism* works end to end and records what the
data actually said. It is not a result about Ponytail's effectiveness: two tiny tasks cannot carry
that claim, and the pilot did not show a benefit. Read the limitations before quoting anything here.

## Setup

- Tasks: **T2** (pagination bug fix) and **T5** (`--json` flag) from [`tasks.md`](tasks.md).
- Arms: **A** = bundle enabled (`defaultMode: full`); **B** = bundle disabled (`plugin_manager
  set_bundle enabled:false`, then restored afterwards).
- Control: fresh agent session per run (same default model, same reasoning settings, no extra
  instructions), verbatim prompt from `tasks.md`, scratch git repository per run.
- Order: all A runs first, then all B runs, because each arm switch remounts the host plugin. This is
  a confound and is listed below.
- Judging: a separate reviewer that did not write the code received the four patches with the arms
  anonymised and the mapping swapped for one task (T2: P = A; T5: P = B). It scored correctness and
  scope discipline 1–5 and named any unrequested abstraction.

## Results

| Task | Arm | Files | ± lines | Tests | Correctness | Scope | Judge note |
|---|---|---|---|---|---|---|---|
| T2 | A (on) | 1 | +2 / −2 | pass | 5/5 | 5/5 | none |
| T2 | B (off) | 1 | +2 / −2 | pass | 5/5 | 5/5 | none |
| T5 | A (on) | 1 | **+5 / −2** | pass | **4/5** | **4/5** | unrequested pretty-print formatting (`JSON.stringify(…, null, 2)`) |
| T5 | B (off) | 1 | +8 / −2 | pass | **5/5** | **5/5** | none |

Totals across the two tasks: correctness A 9/10 vs B 10/10; scope A 9/10 vs B 10/10. Lines added:
A 7, B 10; both touched one file per task and added no tests (the T2 template already ships one).

## What this does and does not show

- **The mechanism works.** The arm switch really changed the session's context (the skill catalog
  emptied in arm B and returned after re-enabling); fresh sessions, verbatim prompts, scratch repos,
  metrics and blind judging all ran without surprises. The kit is usable.
- **No effectiveness signal.** Both arms solved both tasks correctly. The only judgement difference
  came from the bundle-on run adding output formatting nobody asked for — the kind of small
  over-delivery Ponytail is supposed to suppress. On a two-task pilot that is noise, not proof in
  either direction, but it is not a win for the bundle either.
- **These tasks are probably too small.** A two-line bug fix leaves nothing to cut; the rule to
  "take the smallest complete change" has little room to act. The full kit's T1 (config temptation),
  T3 (duplicated refactor), T4 (review with planted bugs) and T6 (retry/backoff) create more room.

## Limitations

1. n = 2 tasks per arm; one model; one machine.
2. Block order: all A then all B. Provider-side changes during the session could bias B.
3. No wall-clock or token counts recorded.
4. T4 (review quality) was not run, so the review skill was not exercised.
5. The judge saw patches only, not the test harness or the repository.

## Next run (the real gate)

Run all six tasks with per-task randomisation, record tokens/time, use two judges (or one judge plus
one human spot-check), and only then apply the pre-registered rule in
[`docs/VERIFICATION.md`](../docs/VERIFICATION.md) L3. Until that exists, the README and release notes must not claim
that the bundle makes changes smaller.

## Reproduce

```bash
# scratch repos under /tmp, one per arm/task, committed baseline
# arm A: bundle enabled; paste the prompt from tasks.md into a fresh session
# arm B: disable the bundle, run the same prompt in a fresh session, re-enable it
git -C /tmp/rein-pilot/T5-A diff --numstat   # +5 / -2
git -C /tmp/rein-pilot/T5-B diff --numstat   # +8 / -2
```

Raw patches from this pilot were used for the blind review and are not committed; the reviewer's JSON
is summarised in the table above.
